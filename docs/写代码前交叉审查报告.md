## 1. P0 阻塞项

### A1 · 文件与附件没有数据模型

**证据**

- 04 §12.12.1 定义了 `POST /api/v1/files/upload`，请求体含 `biz_type`（`EMR_ATTACHMENT` / `VOICE_INPUT` / `OTHER`）与 `session_id`，响应返回 `file_id`、`file_name`、`file_size`。
- 04 §12.12.2 定义了 `GET /api/v1/files/{file_id}`。
- 全文档 `file_id` 出现 8 次，全部在 04。
- **03 中 `mg_file`、`附件`、`object_key`、`file_id`、`MinIO` 出现次数均为 0。**
- 02 §12.2 开发环境端口表有「对象存储 9000/9001」。

**影响**

| 问题 | 说明 |
|---|---|
| 鉴权无从下手 | `GET /files/{file_id}` 必须判断「这个文件属于哪个患者/会话，当前用户有没有权限看」，没有表就查不到归属关系 |
| 生命周期无人管 | 语音文件、点选图上传后在 MinIO 里成为孤儿对象，没有删除与过期策略 |
| 业务关联断裂 | `biz_type=EMR_ATTACHMENT` 的文件应与 `mg_emr_document` 关联，当前无外键关系可依 |
| 存储配额无法统计 | 没有表就统计不出某机构占用了多少对象存储 |

**建议补法**

在 03 新增 `mg_file` 表，并同步更新 init.sql：

```sql
CREATE TABLE IF NOT EXISTS mg_file (
    id              varchar(32)  DEFAULT replace(gen_random_uuid()::text, '-', '') PRIMARY KEY,
    tenant_id       varchar(32)  NOT NULL,
    file_name       varchar(255) NOT NULL,
    file_ext        varchar(16),
    mime_type       varchar(128),
    file_size       bigint       NOT NULL,
    object_key      varchar(500) NOT NULL,
    bucket_name     varchar(128) NOT NULL,
    biz_type        varchar(32)  NOT NULL,
    session_id      varchar(32),
    patient_id      varchar(32),
    biz_ref_id      varchar(32),
    upload_status   varchar(16)  DEFAULT 'DONE',
    create_by       varchar(32),
    create_time     timestamptz  DEFAULT now(),
    update_by       varchar(32),
    update_time     timestamptz,
    del_flag        char(1)      DEFAULT '0',
    remark          varchar(500)
);
```

索引按 03 既有约定，以 `tenant_id` 为首列：

```sql
CREATE INDEX IF NOT EXISTS idx_mg_file_tenant_session ON mg_file (tenant_id, session_id) WHERE del_flag = '0';
CREATE INDEX IF NOT EXISTS idx_mg_file_tenant_biz     ON mg_file (tenant_id, biz_type, biz_ref_id) WHERE del_flag = '0';
CREATE UNIQUE INDEX IF NOT EXISTS uk_mg_file_object_key ON mg_file (object_key);
```

同时补 `biz_type` 枚举说明到 03 的枚举章节：`EMR_ATTACHMENT` / `VOICE_INPUT` / `OTHER`。

### A2 · Redis 键设计缺失

**证据**

- 01 §8.1.1 明确 Redis 承担四项职责：**接口限流（令牌桶）、WebSocket 多实例广播、缓存、消息广播**。
- 02 §7.5 有缓存策略表（5 类缓存：会话热数据 / 知识库检索结果 / 机构配置 / 号源快照 / 限流计数），但只有自然语言描述，如「键构成 = 机构 + 会话标识」。
- 02 §12.1 技术栈：缓存 = Redis。
- **03 中 `Redis`、`cache`、`TTL` 出现次数均为 0**（仅 1 处提到「缓存键以租户标识为前缀」）。
- 04 中依赖 Redis 的机制至少有 4 处：§9 限流（5 种维度）、§11.1 `ws_ticket` 一次性票据、§8 幂等 `Idempotency-Key`、§11 WebSocket 多实例广播。

**影响**

「机构 + 会话标识」这种描述无法直接落成代码。两个人（或两次会话）写出来的键名会撞，且没有统一的过期兜底——Redis 里的 key 会无限堆积。

**建议补法**

在 03 增加附录「Redis 键设计」，或在 02 §7.5 下展开为可执行契约：

| 用途 | 键模式 | 数据结构 | TTL | 说明 |
|---|---|---|---|---|
| 会话热数据 | `mg:sess:{tenant_id}:{session_id}` | Hash | 滑动过期，上限 2h | 会话状态快照，检查点仍以 PG 为准 |
| 知识库检索缓存 | `mg:kbc:{tenant_id}:{query_hash}:{mode}` | String(JSON) | 10 min | `mode` = dense/sparse/hybrid，与 F30 三模式对应 |
| 机构配置 | `mg:cfg:{tenant_id}` | Hash | 30 min | 配置变更时主动 DEL |
| 号源快照 | `mg:slot:{tenant_id}:{dept_code}:{date}` | String(JSON) | 5 min | 短 TTL，容忍陈旧 |
| 限流计数 | `mg:rl:{dimension}:{key}:{window}` | String(计数) | 与窗口一致 | `dimension` 对应 04 §9 的 5 种维度 |
| WS 票据 | `mg:ws:ticket:{ticket}` | String(user_id) | 60 s | 用后即删（`GETDEL`），保证一次性 |
| WS 广播频道 | `mg:ws:chan:{session_id}` | Pub/Sub | — | 同会话消息路由到持有连接的实例 |
| 幂等键 | `mg:idem:{tenant_id}:{idempotency_key}` | String(响应摘要) | 24 h | 与业务唯一键双保险 |

**命名铁律**（建议写入 03）：一律 `mg:` 前缀；`tenant_id` 必须出现在键中（除全局键）；禁止在键中出现明文手机号、身份证号等个人标识。

### A3 · init.sql 与 Alembic 定位冲突

**证据**

| 文档 | 说法 |
|---|---|
| 01 §8.1.1 | `数据结构变更脚本 \| Alembic` |
| 02 §12.1 | `结构变更脚本 \| Alembic` |
| 02 §4.3 目录注释 | `init.sql  # 初始化：扩展、字符集` |
| 02 §9.2 / §9.3 | docker-compose 挂载 `./deploy/postgres/init.sql:/docker-entrypoint-initdb.d/init.sql:ro` |
| **03 §4 实际内容** | init.sql = `CREATE EXTENSION` + **22 张表** + **63 个索引** + 368 个列注释 + 种子数据 |

**冲突点**：02 说 init.sql 只做「扩展、字符集」，但 03 交付的 init.sql 把**全部建表**都做了。

**后果（编码第一天就会遇到）**

1. 容器首次启动，`docker-entrypoint-initdb.d` 执行 init.sql，22 张表建好；
2. 开发者执行 `alembic upgrade head`，Alembic 的 `alembic_version` 表为空，会从头执行第一个 revision → **表已存在，建表失败**；
3. 若强行 `alembic stamp head` 跳过，则版本号是假的，后续变更无法追溯。

**建议补法（二选一，必须写死）**

**方案一（推荐，改动最小）**：init.sql 作为**唯一建表权威**，Alembic 只接管「首次交付之后」的变更。
- 02 §4.3 注释改为 `init.sql  # 初始化：扩展、全部业务表、种子数据`
- 新增流程说明：init.sql 建表后，执行一次 `alembic stamp head` 打基线，此后所有变更走 Alembic
- 03 补一小节说明两者的分工边界

**方案二（更规范，但工作量大）**：init.sql 退回只做 `CREATE EXTENSION vector;` 与建库，22 张表由 Alembic 第一个 revision 生成。需要把 03 §4 的建表脚本改写成 Alembic migration。

考虑到项目当前阶段是「先让本地跑起来」，**建议方案一**，并在文档中注明：若将来移交医院运维，再迁移到方案二。

### A4 · init.sql 实际启用了 RLS，与 03 文档声明矛盾

**证据**

- 03 明确声明（多处）：**一期不启用 RLS，只预留 `tenant_id` 字段与以它为首列的复合索引**；启用步骤见 §6.5「RLS 启用迁移路径」。
- init.sql 实际内容（块注释深度全程为 0，即**不是注释**）：

| 行号 | 语句类型 | 说明 |
|---|---|---|
| 1199 | 行注释 | RLS 相关说明 |
| **1200** | **活 SQL** | `ALTER TABLE mg_session ENABLE ROW LEVEL SECURITY;` |
| 1202 | 行注释 | 策略说明 |
| **1203-1207** | **活 SQL** | `CREATE POLICY ...`（5 行） |

**后果**

直接 `psql -f init.sql` 会**真的启用 RLS**。而一期应用层并未实现 `set_config('app.current_tenant', ...)`，此时：

- 若策略用 `current_setting('app.current_tenant')` 且未设置 → PostgreSQL 抛 `unrecognized configuration parameter` 异常；
- 若策略用 `current_setting('app.current_tenant', true)` → 返回 NULL，`tenant_id = NULL` 恒不成立 → **所有会话查询返回 0 行**。

两种情况下系统都跑不起来，且报错信息具有迷惑性（看起来像数据丢了）。

**建议补法**

把 init.sql 第 1199-1207 行的 RLS 语句**整段注释掉**，并在注释中写明「二期启用时取消注释，同时需实现应用层会话变量注入」；把完整启用脚本单独放到 `deploy/postgres/migrations/001_enable_rls.sql`，与 03 §6.5 的迁移步骤对应。

**同时提醒**：03 §6.5 中提到的关键点——会话变量必须用**事务级** `set_config('app.current_tenant', ?, true)`，否则连接池复用会导致租户串号——这条很重要，建议在 03 §6.5 用醒目方式标注（目前只是一行表格文字）。

### A5 · 审计表权限回收被注释，但文档声称已做

**证据**

- 03 中 `mg_audit_log` 表定义处写：「**不可修改** \| 数据库层面回收该表的 UPDATE / DELETE 权限（见 init.sql 末尾）」
- init.sql 实际内容：

| 行号 | 内容 | 状态 |
|---|---|---|
| 1172 | `REVOKE UPDATE, DELETE ON mg_audit_log FROM PUBLIC;` | **被注释**（comment=1） |
| 1173 | `GRANT SELECT, INSERT ON mg_audit_log TO medguide_app;` | **被注释**（comment=1） |

**后果**

「审计日志不可篡改」是安全设计的一个卖点，但**数据库层面并没有真正拦住**。写代码时如果有人不小心写了 UPDATE，不会有任何阻碍。

**建议补法（三选一）**

1. **放开注释并确认角色名**：需要先在 init.sql 中创建应用角色 `medguide_app`，或改为对当前连接用户回收权限。注意容器默认超级用户是 `postgres`，对超级用户 REVOKE 不生效——需在文档里说明「该约束对超级用户无效，生产环境必须使用非超级用户连接」。
2. **保留注释但改文档措辞**：把 03 的「不可修改」改为「应用层禁止修改；数据库层权限回收见 init.sql 末尾（默认注释，生产环境启用）」。
3. **加触发器**：用 `BEFORE UPDATE OR DELETE` 触发器直接 `RAISE EXCEPTION`。这条对超级用户也有效，是三者中最硬的。

**建议**：选方案 3 或方案 2+3 组合，因为方案 1 对超级用户失效，容易给人虚假的安全感。

## 2. P1 一致性缺陷

### B1 · 开发期云端 API 与「数据不出域」的落地缺口 ★最高价值

**证据**

- 用户目标：**先把项目在本地电脑跑起来**（本地无 GPU，模型必须走云端 API）。
- 01 §8.1.3：`NFR56` 含患者数据的全部处理环节不得出院内网络；`NFR55` 必须支持院内网私有化部署。
- 02 §8.2 出域守卫：按「能力 + 地址」双维度判定，**患者数据能力在任何环境都拒绝院外地址**。
- 02 §9.2 开发环境：「开发期内容生成与精排可能指向院外服务。此时出域守卫按『开发策略』放行**非患者数据**能力；涉及患者数据的能力仍被拒绝。」

**冲突点**：预问诊主流程 `F01 → F02（患者输入主诉）→ F33（导诊分流）` 中，**患者主诉本身就是患者数据**，必须送进 LLM 才能完成分流。按 02 §9.2 的规则，开发期这条链路会被出域守卫拒绝 → **本地主流程根本跑不通**。

这是一个**设计正确、但与项目当前阶段目标冲突**的问题。不解决，用户「先跑起来」的目标无法达成。

**建议补法：引入显式的开发期出域策略（而不是悄悄放宽）**

新增配置项 `EGRESS_POLICY`，取值为 `strict`（交付期默认）或 `dev_sandbox`（开发期）：

| 约束 | 内容 |
|---|---|
| 数据约束 | `dev_sandbox` 下**只允许使用合成病例**（`kb/tests/synthetic_cases.yaml`），禁止接入任何真实患者信息 |
| 审计约束 | 每条放行的出域调用写一条 `mg_audit_log`，`action_type = EGRESS_DEV`，便于交付前核查 |
| 可见性约束 | 启动日志打印醒目 WARNING；`GET /api/v1/system/info` 返回 `egress_policy` 字段；前端顶部显示红色横幅「当前为开发模式，含合成数据出域」 |
| 交付约束 | 当 `DEPLOY_MODE = prod` 且 `EGRESS_POLICY = dev_sandbox` 时，**启动校验直接拒绝启动**（复用 02 §10.3 既有的校验机制） |

这样做的价值：既让本地开发跑得通，又保住了「数据不出域」架构的完整性。面试被问到「你怎么在没 GPU 的情况下开发」时，这本身就是一个可讲的答案——**用策略开关 + 合成数据 + 审计留痕来隔离开发期与交付期的数据边界**。

同时建议在 02 §8.2 出域守卫的状态机图中补上 `EGRESS_POLICY` 这个分支，并在 01 §8.1.3 补一条 `NFR70`（或并入 `NFR56` 的说明）来承载这个策略。

### B2 · EMR / 病历 术语不统一

**证据**

| 文档 | 出现情况 |
|---|---|
| 01 | `EMR` 3 次、`SOAP` 15 次 |
| 02 | **`EMR` 0 次**、`电子病历` 0 次；统一用「病历」（`emr_writer.py # 病历生成`、`emr_record_mcp.py # 病历查询`） |
| 03 | `EMR` 3 次（`mg_emr_record`、`mg_emr_document`、审计 `action_type=EMR_READ`） |
| 04 | `EMR` 26 次（接口路径 `/sessions/{id}/emr`） |

**判定**：这是**术语不统一，不是功能缺失**。02 用「病历」表达同一概念，功能设计是完整的（有 `emr_writer.py`、`emr_record_mcp.py`、追溯矩阵中 F36/F45/F46 均有落点）。

**影响**：影响的是代码命名与文档检索。开发时搜「EMR」在架构文档里搜不到，容易误判为「架构没设计」。

**建议补法**：在 02 §1.4 术语表加一条「病历 / EMR（Electronic Medical Record）：本文档统一称『病历』，数据库表与接口路径使用 `emr` 前缀」。或者在 04 §1.3 术语表明确两者同义。**不要全文替换**——替换成本高且容易引入新错误。

### B4 · 19 条 NFR 追溯链断裂

### B5 · Celery 任务清单缺失

**证据**

- 02 §12.1 技术栈：`异步任务 | Celery`
- 02 §4.2 目录结构：`jobs/ # ── 异步任务`
- 02 有多处提到「异步任务」（`F28` 发布、`F29` 入库、`F31` 回归、`F32` 回滚二期）
- **但没有 Celery 的任务清单、队列划分、重试策略、broker 配置**

**影响**：写 `jobs/` 目录时不知道要写几个任务、任务名怎么定、队列怎么分、失败怎么重试。

**建议补法**：在 02 §5.6（知识库构建组件）或 §10 增补一小节「异步任务清单」：

| 任务 | 触发方式 | 队列 | 幂等键 | 重试策略 |
|---|---|---|---|---|
| 知识库全量入库 | `POST /admin/kb/tasks/ingest` | `kb` | `task_id` | 最多 3 次，指数退避 |
| 知识库发布 | `POST /admin/kb/publish` | `kb` | `publish_version` | 不自动重试（需人工确认） |
| 黄金查询回归 | `POST /admin/retrieval/verify` | `eval` | `run_id` | 最多 2 次 |
| 语音转写 | `POST /patient/asr/transcribe` | `asr` | `file_id` | 最多 2 次 |

并明确：**broker 与 result backend 复用 Redis，使用独立 db 编号**（如 broker=`db 1`，限流/缓存=`db 0`），避免 `FLUSHDB` 误伤。

### B6 · 本地 BGE-M3 推理路线未固化

**证据**

- 01 §8.1.1：`向量化模型 | BGE-M3（一次推理同时产出稠密向量与稀疏向量）` —— 只说用什么模型，没说**用什么库跑**。
- 02 §10.3 启动校验：要检查「本地向量化模型的路径不存在或缺少必要文件」→ 拒绝启动；「本地向量化模型缺少稀疏检索权重」→ 告警。
- 02 §12.5 风险 #4：本地向量化成为启动依赖，缓解措施是「懒加载」。
- **但没有任何文档写明推理实现方式。**

**影响**：这直接决定 `requirements`/`pyproject` 的依赖与镜像体积。

| 方案 | 依赖 | 体积影响 | 说明 |
|---|---|---|---|
| FlagEmbedding | `torch` + `transformers` + `FlagEmbedding` | **+2 GB 以上** | 代码约 20 行 |
| ONNX Runtime | `onnxruntime` + `tokenizers` + `numpy` | **约 +200 MB** | 需自行实现稀疏权重计算，约 200 行 |
| 云端 API | 无本地依赖 | 0 | 但 API 版 bge-m3 **只返回稠密向量，不返回稀疏词元权重** |

**建议补法**：在 01 §8.1.1「检索与知识库」分块中补一行「本地向量化推理实现」，明确选择。若选 ONNX Runtime，需在文档中说明「稀疏权重由 `relu(token_embeddings @ W.T + b)` 计算并按 token_id 取 max 得到」，因为这是自行实现的部分，不写下来后面没人知道。

**注意**：这一步的选择会反过来影响 A2 中「混合检索」是否可用——若最终只能拿到稠密向量，则 02 §12.5 风险 #3（词元检索增益未验证）会自动变成「词元检索不可用」，`ADR-005` 的开关要相应调整。
