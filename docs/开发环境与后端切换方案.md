# 开发环境与模型后端切换方案

> 本文档解决的问题：项目要求生产环境模型私有化部署（数据不出域），但开发机硬件无法承载本地模型与容器化中间件。方案目标是**一套业务代码，三套运行环境，切换只改配置**。

---

## 1. 问题与约束

### 1.1 开发机硬件实测

| 项 | 实测值 | 结论 |
|---|---|---|
| GPU | NVIDIA GeForce MX450，**2 GB 显存** | 连 7B 量化模型（约需 5 GB）都无法加载，本地推理不可行 |
| 内存 | 15.8 GB 总量，**当前可用 3.1 GB** | Docker 同时运行 Milvus + PostgreSQL + Redis 需 5~6 GB，装不下 |
| CPU | 4 逻辑核心 | 够用 |
| 磁盘 | C 盘 35 GB / D 盘 56 GB 可用 | 够用（模型权重不落地，占用可控） |

### 1.2 由此得出的两条硬约束

| 编号 | 约束 | 说明 |
|---|---|---|
| `DEV-01` | **模型推理必须走云端 API** | 2 GB 显存无法加载任何可用的量化模型 |
| `DEV-02` | **中间件不能容器化** | 内存不足，Milvus / PostgreSQL / Redis 三件套无法同时以容器运行 |

> 注意：`DEV-02` 的实际影响比 `DEV-01` 更大。多数人只关注显存不足，但真正会卡住开发的是**内存不足导致中间件起不来**。

---

## 2. 核心原则：一套代码，三套环境

三套环境共用同一份业务代码，差异全部收敛到配置层。切换靠四项环境变量：

| 环境变量 | 决定 |
|---|---|
| `LLM_BASE_URL` | 内容生成走云端 API 还是本地推理服务 |
| `EMBEDDING_BASE_URL` | 向量化走云端 API 还是本地服务 |
| `MILVUS_URI` | 向量库是本地文件还是集群地址 |
| `DATABASE_URL` | 关系库是 SQLite 还是 PostgreSQL |

**实现前提**：所有组件都通过**标准协议**接入，业务代码不感知具体实现。

- 内容生成与向量化：统一使用 OpenAI 兼容协议（云端 API、本地推理服务、本地向量化服务均支持）
- 向量库：统一使用 `MilvusClient` 接口
- 关系库：统一使用 SQLAlchemy ORM

---

## 3. 三套环境的组件对照

| 组件 | 开发期（本机） | 验证期（GPU 云） | 交付期（院内） |
|---|---|---|---|
| 内容生成 | 云端 API | 本地 vLLM | 本地 vLLM / 国产算力 |
| 向量化与精排 | 云端 API | 本地服务化部署 | 本地服务化部署 |
| 向量库 | Milvus Lite（单文件） | Milvus Standalone（容器） | Milvus 集群 |
| 关系库 | SQLite | PostgreSQL | PostgreSQL |
| 缓存 | 进程内存 | Redis | Redis |
| 会话状态持久化 | SQLite | PostgreSQL | PostgreSQL |
| 语音识别 | 跳过（文字测试） | 本地 FunASR | 本地 FunASR |
| 链路追踪 | 关闭 | 自托管 | 自托管 |
| 出域守卫 | 放行非患者数据 | 放行非患者数据 | 全链路拦截 |

## 4. 开发期具体方案

### 4.1 模型服务：必须选「与生产同源」的 API

这是整份方案里最关键的一条。**不要随便挑一个便宜的大模型 API，要挑生产环境将要用到的那个开源模型的 API 版本。**

| 环节 | 生产（本地） | 开发期（API） | 是否同源 |
|---|---|---|---|
| 主推理 | Qwen2.5-32B-Instruct（AWQ 量化） | `Qwen/Qwen2.5-32B-Instruct` | ✅ 同一模型 |
| 轻量任务 | Qwen2.5-7B-Instruct | `Qwen/Qwen2.5-7B-Instruct` | ✅ 同一模型 |
| 向量化 | BAAI/bge-m3 | `BAAI/bge-m3` | ✅ **向量空间完全一致** |
| 结果精排 | bge-reranker-v2-m3 | `BAAI/bge-reranker-v2-m3` | ✅ 同一模型 |
| 语音识别 | FunASR + Paraformer | 跳过 | — |

**服务商选择**

| 服务商 | 可提供的同源模型 | 评价 |
|---|---|---|
| 硅基流动 | Qwen2.5-32B、bge-m3、bge-reranker-v2-m3 | **首选**，全套与生产同源，有免费额度 |
| 阿里云百炼 | qwen2.5-32b；但其向量模型为 text-embedding-v3 | 对话可同源，**向量模型不同源**，需注意 |
| 其他通用大模型 API | 仅有对话模型 | 仅适合做输出质量对比，不适合作为主力 |

**更优解：向量化本地跑，不必走 API。**

若本机已有完整 BGE-M3 权重（需含 `sparse_linear.pt` 与 `colbert_linear.pt`，这才是完整版），可直接在本机 CPU 上推理：

| 优势 | 说明 |
|---|---|
| 零 API 成本 | 灌库时向量化是 token 消耗最大的一环 |
| 彻底避开"向量模型不同源"的风险 | 开发期与生产用同一份权重，向量空间完全一致 |
| **不依赖 Milvus 内置 BM25** | BGE-M3 一次推理可同时产出稠密向量与稀疏词元权重，两者共同写入 Milvus，因此无需 Milvus 的 BM25 Function —— 同时绕开了 Milvus Lite 的版本能力差异 |
| 便于数据出域合规 | 向量化这一步不产生任何院外请求 |

**代价与应对**

| 问题 | 应对 |
|---|---|
| fp32 权重约占 2.2 GB 内存 | 做 ONNX int8 动态量化，降至约 0.6 GB，CPU 速度还能提升 2~4 倍 |
| 精排（交叉编码器）在 CPU 上慢 | 开发期把精排候选数收敛到 8 条；生产环境上 GPU 后再放开到 20~30 条 |

**稀疏向量的度量方式随之改变**：由于稀疏向量由 BGE-M3 产出而非 Milvus 生成，索引的 `metric_type` 应设为 `IP`，**不是 `BM25`**。

**⚠️ 最重要的警告：不要混用向量模型。**

如果开发期用 A 模型的向量、生产环境换成 bge-m3，则：

1. 知识库必须**全量重新向量化**
2. 混合检索的融合权重、精排阈值**全部需要重新调优**
3. 黄金查询集的期望结果可能失效

**用 `bge-m3` 的 API 版本，可以让开发期调好的检索效果直接迁移到生产。**

### 4.2 向量库：Milvus Lite

Milvus Lite 直接运行在 Python 进程内，数据落在单个本地文件，**无需任何容器或独立服务**。

```python
from pymilvus import MilvusClient

# 本地文件模式
client = MilvusClient("./data/milvus_dev.db")

# 生产环境只需换成集群地址，业务代码不变
# client = MilvusClient(uri="http://milvus.intranet:19530")
```

**安装**

```bash
pip install -U "pymilvus[milvus-lite]"
```

**能力核对（本项目所需项）**

| 能力 | 是否支持 |
|---|---|
| 稠密向量检索 | ✅ |
| 稀疏向量检索 | ✅ |
| BM25 全文检索 | ✅（通过 Schema Function 定义） |
| 混合检索（RRF / 加权融合） | ✅ |
| 标量过滤（含 JSON、数组、文本匹配） | ✅ |
| 倒排索引（标量 / 稀疏） | ✅ |
| HNSW / IVF 等向量索引 | ✅ |
| 分区键路由 | ✅ |
| 多进程并发写入 | ❌ 单进程（文件锁保护） |
| 认证 / 角色 / TLS | ❌ 无 |

**⚠️ 版本差异风险（必须在开发第一天验证）**

Milvus Lite 存在两代实现，**同名但能力不同**：

- 早期实现基于 C++ 封装：仅支持 FLAT 索引，**不支持全文检索与 BM25**
- 新版为纯 Python 重写：支持 BM25、混合检索、分区键与多种索引

**验证脚本**——第一件事就是跑通它：

```python
from pymilvus import MilvusClient, DataType, Function, FunctionType

client = MilvusClient("./data/probe.db")
schema = client.create_schema(auto_id=True)
schema.add_field("id", DataType.INT64, is_primary=True)
schema.add_field("text", DataType.VARCHAR, max_length=4096, enable_analyzer=True)
schema.add_field("dense", DataType.FLOAT_VECTOR, dim=1024)
schema.add_field("sparse", DataType.SPARSE_FLOAT_VECTOR)
schema.add_function(Function(
    name="bm25", function_type=FunctionType.BM25,
    input_field_names=["text"], output_field_names=["sparse"],
))
client.create_collection("probe", schema=schema)
print("BM25 与混合检索可用")
```

若该脚本报错，按顺序降级：

| 降级方案 | 说明 |
|---|---|
| 1. 在 WSL2 中运行 Milvus Standalone | 绕开 Windows 兼容性问题，但内存需求仍存在 |
| 2. 使用 Zilliz Cloud 免费层 | 开发期只用合成数据，可接受 |
| 3. 检索层换用本地轻量实现 | 需保证检索层已抽象为接口，可切回 Milvus |

> 无论走哪条路，**检索层都必须抽象为接口**（`Retriever` 协议），这是保证可切换的前提。

### 4.3 关系库与缓存

| 组件 | 开发期方案 | 切换说明 |
|---|---|---|
| 关系库 | SQLite（`sqlite+aiosqlite`） | 与 PostgreSQL 共用同一套 ORM 定义 |
| 缓存 | 进程内字典 | 生产替换为 Redis 客户端，接口一致 |
| 会话状态持久化 | SQLite | 生产替换为 PostgreSQL |

**SQLite 的注意事项**

- 不支持高并发写入 —— 开发期单用户，无影响
- **字段类型不要使用 PostgreSQL 专有类型**（如 JSONB），统一用 SQLAlchemy 的通用 `JSON` 类型，否则切换到 PostgreSQL 时需改表
- 迁移脚本（Alembic）需能在两种数据库上执行

### 4.4 语音识别

开发期**跳过**。理由：语音识别需要本地模型，2 GB 显存无法承载；而语音输入的本质是"把语音转成文字"，转写之后的流程与文字输入完全相同。

做法：

- 语音输入接口保留，实现为空（返回"当前环境未启用"）
- 全部流程测试通过文字输入完成
- 语音能力在验证期用 GPU 云补齐

### 4.5 可观测

| 阶段 | 方案 |
|---|---|
| 开发期 | 关闭链路追踪，或仅在本地打印结构化日志 |
| 验证期与交付期 | 自托管追踪服务 |

**注意**：开发期若启用云端追踪服务，上报内容会包含 prompt 原文。**开发期只能用合成数据**，这是下面出域策略成立的前提。

**代码只读取配置，不判断环境**

```python
class Settings(BaseSettings):
    app_env: Literal["development", "local_gpu", "production"] = "development"
    egress_policy: Literal["development", "on_prem"] = "development"

    llm_base_url: str
    llm_model: str
    small_llm_model: str
    embedding_base_url: str
    embedding_model: str
    rerank_model: str

    milvus_uri: str
    database_url: str
    redis_url: str = ""
    checkpoint_backend: Literal["sqlite", "postgres"] = "sqlite"

    asr_enabled: bool = False
    tracing_enabled: bool = False
```

**禁止事项**：业务代码中出现 `if settings.app_env == "development"` 这类分支。环境差异必须全部由配置值驱动，否则代码会分叉成两套。

## 6. 出域守卫：按能力分级，不是简单开关

开发期允许调用云端 API，但**不能因此放开所有出域限制**。正确的设计是按能力分级：

```python
class EgressGuard:
    """含患者标识的能力，无论何种环境一律禁止出域；其余能力按部署策略判定。"""

    PII_CAPABILITIES = {
        "emr_query",            # 既往病历查询
        "patient_profile",      # 患者信息读取
        "asr_realtime",         # 真实患者语音
        "kb_emr_retrieval",     # 病历文书检索
    }

    def check(self, capability: str, target_url: str) -> None:
        host = urlparse(target_url).hostname or ""

        # 第一道：与患者数据相关的能力，任何环境都不出域
        if capability in self.PII_CAPABILITIES and not is_private_host(host):
            raise DataResidencyViolation(
                f"能力 {capability} 涉及患者数据，不得访问外部地址：{host}"
            )

        # 第二道：院内网模式下，一律禁止外部地址
        if settings.egress_policy == "on_prem" and not is_private_host(host):
            raise DataResidencyViolation(f"院内网模式禁止访问外部地址：{host}")
```

**三道防线的作用**

| 场景 | 结果 |
|---|---|
| 开发期用合成数据调云端 API | 放行（合规，无患者数据） |
| 开发期误接真实病历调云端 | **被第一道拦截** |
| 生产期任何外部地址 | 被第二道拦截 |
| 开发期用地址直连绕过域名 | 按地址段判定，同样拦截 |

## 7. 开发期与生产的行为差异及对策

切换后端不是"改个地址就完事"，以下六点是真实的坑：

| 差异点 | 风险 | 对策 |
|---|---|---|
| **结构化输出** | 云端 API 的 JSON Schema 约束与本地推理引擎的受约束解码行为可能不同 | 统一用 Pydantic 校验兜底；校验失败重试一次，再降级为纯文本 |
| **上下文长度** | 云端可能支持 128K，本地 32B 实际可用约 32K | **按本地的较小值设计 Prompt 总量上限**，不依赖云端的长上下文 |
| **限流** | 云端有请求频率限制，本地无 | 客户端加指数退避重试与请求排队 |
| **量化差异** | AWQ 量化模型与非量化模型输出存在细微差别 | 关键用例在两种后端各跑一遍，**比对输出结构而非文本内容** |
| **BM25 统计口径** | Milvus Lite 的词频权重为分段级统计，集群为全局统计 | 切换后**重跑黄金查询回归**，重新校准融合权重 |
| **并发能力** | 云端可承载高并发，本地单卡约 10 路 | 开发期压测结果**不可作为生产并发指标** |

**建议：建立双后端回归测试。** 关键用例（分诊路由、危重症拦截、病历字段完整性）在两种后端各执行一遍，断言输出结构与关键字段一致。这是唯一能提前发现切换风险的手段。

## 8. 交付前检查清单

打包交付前逐项确认，任一不通过则不允许发布：

- [ ] `EGRESS_POLICY` 是否为 `on_prem`
- [ ] `LLM_BASE_URL` 与 `EMBEDDING_BASE_URL` 是否指向内网地址
- [ ] 代码与配置中是否存在硬编码的云端 API 凭证
- [ ] `MILVUS_URI` 与 `DATABASE_URL` 是否指向院内实例
- [ ] `TRACING_ENDPOINT` 是否为自托管地址
- [ ] `ASR_ENABLED` 为 `true` 且指向本地语音服务
- [ ] 抓包确认零外网请求
- [ ] 黄金查询回归通过率不低于基线
- [ ] 用真实规模数据（建议 ≥ 10 万条向量）压测，确认延迟指标
- [ ] 双后端回归测试全部通过

前 6 项可脚本化，做成部署门禁自动执行。

## 9. 成本与升级路径

### 9.1 开发期 API 成本量级

按知识库约 5000 条、评测集 200 例、日常调试对话数百轮估算：

| 项目 | 量级 |
|---|---|
| 对话推理（Qwen2.5-32B） | 约 60 万 token |
| 向量化（bge-m3） | 约 100 万 token |
| **合计花费** | **约 10~50 元**（具体单价以服务商为准） |

开发期用云端 API 的成本可以忽略，**真正的成本是时间**。

### 9.2 硬件升级路径

| 阶段 | 配置 | 用途 |
|---|---|---|
| 开发期 | 本机现有配置 | 业务逻辑开发，模型全走 API |
| 验证期 | 按小时租用 GPU 云（1×4090 24G 或 1×A100 40G） | 跑通本地部署全流程 |
| 演示期 | 同上 | 现场演示本地模型 |

### 9.3 强烈建议：至少租一次 GPU 云

**理由**：项目在需求文档中承诺了「数据不出域、模型本地部署」。这个承诺如果从未被验证过，面试或答辩时被问一句"你怎么确认本地部署可行"就无法回答。

**租用一次 GPU 云可以做到**：

1. 用 vLLM 部署 Qwen2.5-32B-AWQ，跑通端到端问诊流程
2. 用容器部署 Milvus Standalone，验证混合检索与 Lite 版本结果一致
3. 记录吞吐与延迟实测数据
4. 留存部署过程与运行截图

**一次租用成本几十元**，换来的是"本地部署可行"这句话的可信度。

### 9.4 统一表述

对内对外统一使用以下表述，避免含糊：

> 开发阶段使用云端 API 验证业务逻辑与检索策略，生产环境采用全本地私有化部署；本地部署的可行性与性能已在 GPU 服务器上完成验证。

### 附 2.2 三个必须提前知道的限制

| # | 限制 | 影响 | 应对 |
|---|---|---|---|
| 1 | **关闭浏览器或断网会导致实例被释放** | 容器整体销毁，`tmux`、`nohup` 均无效 | 验证期间保持页面开启；长任务改用离线训练任务 |

| 3 | **按时长计费，挂机同样扣除** | 闲置时开着页面会白耗额度 | 用完立即关机 |

> 第 3 点决定了使用策略：**GPU 时长要花在"跑"上，不能花在"配环境"和"下模型"上。**

### 附 2.3 使用策略：CPU 环境备料，GPU 环境一次跑完

关键做法是**用永久免费的 CPU 环境完成所有准备工作**：

| 阶段 | 用哪个环境 | 做什么 | 消耗 GPU 额度 |
|---|---|---|---|
| 备料 | CPU 环境（不限时长） | 写好全部脚本、下载模型权重到 `/mnt/workspace`、装依赖 | **0** |
| 验证 | GPU 环境（36 小时/月） | 一次性执行验证脚本，采集数据与截图 | 实际运行时长 |
| 收尾 | GPU 环境 | 立即关机 | — |

> 需先确认 CPU 实例与 GPU 实例挂载的是**同一块 `/mnt/workspace`**（同一账号下通常共享，首次使用时验证一次即可）。若不共享，则改为在 GPU 环境内先下模型再跑验证，但要一次性完成。

### 附 2.5 显存分配的取舍

24 GB 无法同时容纳 32B 模型与完整检索链路，需分时执行两套配置：

| 方案 | 配置 | KV 缓存余量 | 可支撑并发 | 用途 |
|---|---|---|---|---|
| A | 仅 32B-AWQ（权重约 20 GB） | 4 GB | 约 4 路（4K 上下文） | 验证主推理质量与吞吐 |
| B | 14B-AWQ + 向量化 + 精排（合计约 14.3 GB） | 9.7 GB | **约 12 路（4K 上下文）** | 验证完整链路与并发能力 |

**重要提示**：方案 B 的并发上限（约 12 路）已超过需求文档 `NFR11` 的「单机支持 ≥ 10 路并发会话」。在 A10 上跑方案 B 即可完成该指标的实测验证。
