## 1. 数据库设计规范

### 1.1 命名规范

| 对象 | 规范 | 示例 | 说明 |
|---|---|---|---|
| 表 | `mg_` + 小写下划线 | `mg_session` | 统一前缀。框架自管表放独立 schema，不使用该前缀 |
| 字段 | 小写下划线 | `create_time` | 全小写，单词间用下划线 |
| 主键 | 统一为 `id` | `id` | 32 位无连字符字符串 |
| 租户字段 | 统一为 `tenant_id` | `tenant_id` | 复合索引首列 |
| 逻辑关联字段 | 关联表名 + `_id` | `session_id` | 逻辑关联，不建物理外键 |
| 编码 / 业务编号 | `_code` / `_no` 后缀 | `dept_code`、`appointment_no` | 与主键区分 |
| 状态 / 枚举 | `status` | `status` | 取值见附录 6.3 |
| 布尔语义 | `is_` 前缀 | `is_active` | 用 `char(1)` 表示 |
| 标记类 | `_flag` 后缀 | `del_flag`、`risk_flag` | 用 `char(1)` 表示 |
| 时间 | `_time` 后缀 | `create_time`、`expire_time` | 一律用带时区的类型 |
| JSON 字段 | `_json` 后缀 | `candidates_json` | 承载快照式附属数据 |
| 索引 | `idx_` + 表名 + 字段 | `idx_mg_session_tenant_status` | 见 1.5 节 |
| 唯一索引 | `uk_` + 表名 + 字段 | `uk_mg_user_tenant_account` | 见 1.5 节 |

### 1.2 主键规范

| 项 | 规范 |
|---|---|
| 类型 | `varchar(32)` |
| 默认值 | `replace(gen_random_uuid()::text, '-', '')` |
| 生成方式 | 数据库默认值，应用层无需生成 |
| 格式 | 32 位十六进制小写字符串，**无连字符** |
| 依赖扩展 | 无。`gen_random_uuid()` 为 PostgreSQL 13+ 内置函数，**不需要 `pgcrypto`** |
| 为何不用自增整数 | 自增主键会暴露业务量、不利于分库与数据迁移、插入时依赖序列造成争用 |
| 为何不用带连字符的 UUID | 32 位定长更紧凑，且索引与比较效率更高 |

**种子数据的固定标识规则**：种子数据使用可读的 32 位标识，格式为「全零 + 序号」，便于识别与幂等插入。

```
默认租户        00000000000000000000000000000001
默认机构管理员  00000000000000000000000000000002
默认知识库管理员 00000000000000000000000000000003
默认模型厂商    00000000000000000000000000000004
```

### 1.3 审计字段规范

所有业务表必须包含以下字段。**不使用触发器**，`update_time` 与 `update_by` 由应用层统一维护。

| 字段名 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `tenant_id` | `varchar(32)` | NOT NULL | 租户标识。**所有复合索引的首列** |
| `create_by` | `varchar(32)` | | 创建人标识。系统自动创建时填 `system` |
| `create_time` | `timestamptz` | NOT NULL DEFAULT `now()` | 创建时间 |
| `update_by` | `varchar(32)` | | 最后更新人标识 |
| `update_time` | `timestamptz` | | 最后更新时间。**由应用层写入，不依赖触发器** |
| `del_flag` | `char(1)` | NOT NULL DEFAULT `'0'` | 软删除标记：`0` 正常，`1` 已删除 |
| `remark` | `varchar(500)` | | 备注 |

**审计字段的语义分层**（重要）

`del_flag` 字段在所有业务表上统一存在，但**实际语义按表类型分层**，避免概念混淆：

| 表类别 | `del_flag` 是否实际使用 | 说明 |
|---|---|---|
| 配置类 / 主数据 | ✅ **使用** | 停用即置 `'1'`，保留数据与历史。表：租户、科室、用户、知识库条目、模型配置、黄金查询集 |
| 事务类数据 | ❌ **恒为 `'0'`** | 不做软删除，靠**保留期归档**清理。表：会话、消息、结论、病历、挂号、授权 |
| 只追加表 | ❌ **不设该字段** | 审计记录、知识库变更记录。在只追加表上挂"可删除标记"与"不可修改"要求矛盾 |

**为何统一带字段**：仓储基类可以无差别注入 `del_flag = '0'` 过滤条件，不需要为每张表写特例——这与"机构过滤不可绕过"采用同一套机制。

**为何不用触发器维护时间戳**：触发器是隐式行为，调试时难以追踪；且应用层已掌握完整的操作上下文，由应用层写入比触发器更可控。代价是**任何绕过服务层的直接写库都会漏掉时间戳**——这是团队必须知晓的约定。

### 1.4 外键策略

**不使用数据库级外键约束**，采用「逻辑关联 + 索引」。

| 项 | 做法 |
|---|---|
| 关联表达 | 关联表名 + `_id` 字段（如 `session_id`） |
| 完整性保障 | 应用层在服务层校验 + 定期数据质量巡检 |
| 查询性能 | 为每个逻辑关联字段建立索引 |
| 删除策略 | 不使用级联删除。配置类走软删除；事务类不做删除；归档由定时任务按保留期执行 |

**不用外键的四条理由**

| 理由 | 说明 |
|---|---|
| 写入性能 | 每次写入都要校验引用完整性，高并发写入场景下成为瓶颈 |
| 运维灵活性 | 外键会让数据迁移、批量导入、分区改造变得困难 |
| 分区友好 | 带外键的表无法灵活分区，而本项目所有表都要按租户维度组织索引 |
| 与软删除冲突 | 软删除的数据物理上仍存在，外键约束反而无法表达"逻辑已删除"的语义 |

**代价与补偿**

| 代价 | 补偿措施 |
|---|---|
| 可能出现孤儿记录 | 服务层校验 + 定期巡检脚本 |
| 无法依赖数据库报错发现关联错误 | 集成测试覆盖主要关联路径 |

**审计表为何不建任何关联**：`mg_audit_log` 不与其他表建立逻辑关联字段（除 `tenant_id`），只记录标识快照。理由：审计记录必须独立于业务数据的存在状态——若业务数据被归档清理，审计仍须可读。

### 1.5 索引策略

| 索引类型 | 用途 | 适用场景 |
|---|---|---|
| B-tree（复合） | 等值 + 范围查询 | 列表分页、状态筛选、时间排序 |
| B-tree（唯一） | 唯一性约束 | 租户内账号唯一、业务编号唯一 |
| GIN | JSONB 内部键值检索 | 查询"哪些结论推荐了消化内科"这类 JSONB 内字段 |
| GIN + 全文 | 文本模糊检索 | 知识库条目搜索（`F24`） |
| 部分索引 | 只索引满足条件的行 | 只索引未删除数据、只索引待处理任务 |
| HNSW（向量库） | 向量近邻检索 | 见 1.7 节 |

**复合索引的设计原则**

| 原则 | 说明 |
|---|---|
| **`tenant_id` 恒为首列** | 所有业务查询都带租户条件，首列放它才能命中索引 |
| 第二列放筛选区分度高的字段 | 通常是 `status`、`del_flag`、`session_id` 等 |
| 末列放排序字段 | 配合 `ORDER BY` 避免额外排序 |
| 控制索引数量 | 单表索引不超过 5 个，写多读少的表进一步收紧 |
| 优先用部分索引 | 未删除数据通常占多数，用 `WHERE del_flag = '0'` 缩小索引体积 |

**索引命名规则**

```
idx_<表名>_<字段1>_<字段2>      普通复合索引
uk_<表名>_<字段1>_<字段2>       唯一索引
idx_<表名>_<字段>_gin           GIN 索引
idx_<表名>_<字段>_partial       部分索引
```

### 1.6 多租户隔离

| 层 | 做法 |
|---|---|
| 字段 | 所有业务表带 `tenant_id` |
| 索引 | 所有复合索引以 `tenant_id` 为首列 |
| 查询过滤 | **仓储基类统一注入** `tenant_id` 条件，业务代码不手写 |
| 行级隔离 | 医生与患者的接诊归属关系在服务层校验（`R07`） |
| 缓存 | 缓存键以租户标识为前缀 |
| 向量库 | `tenant_id` 作为分区键 + 检索时强制过滤 |

**不启用数据库级行级安全策略（RLS）**

当前交付形态为**单机构私有化部署**，只有 1 个租户，数据库级 RLS 的实际防护收益接近零，但会带来三项成本：每张表需维护策略、应用层需在事务内设置会话变量、开发调试时易因漏设变量而"查不到数据"。

**但表结构已完整预留**：`tenant_id` 字段与以它为首列的复合索引全部就位。**将来启用 RLS 是纯增量动作，不需要改表结构**。完整迁移步骤见附录 6.5。

### 1.7 向量存储规范

向量库承担知识库检索，与业务库的分工和一致性边界见架构文档 §7.1、集合划分理由见 §7.3。本节给出**执行级参数**。

| 规范项 | 取值 | 说明 |
|---|---|---|
| 向量维度 | **1024** | 与向量化模型输出维度一致 |
| 稠密向量类型 | `FLOAT_VECTOR` | |
| 稀疏向量类型 | `SPARSE_FLOAT_VECTOR` | 由向量化模型产出，非向量库生成 |
| 向量索引类型 | **HNSW** | |
| HNSW 参数 — M | **16** | 每个节点的最大出边数 |
| HNSW 参数 — efConstruction | **64** | 建索引时的搜索宽度 |
| 稠密度量方式 | **余弦相似度** | 与向量化模型训练目标一致 |
| 稀疏度量方式 | **内积（IP）** | **不是 BM25**。稀疏向量由模型产出，两路向量打分口径需一致 |
| 索引参数可调性 | HNSW 参数随数据规模调整 | 见附录 6.6 |
| 分区键 | `tenant_id` | 除编码对照集合外全部按租户分区 |
| 主键字段 | `id`（varchar 32） | 与业务库保持同一标识格式 |
| 文本字段 | `text`（启用分词） | 供稀疏检索与全文匹配使用 |
| 元数据字段 | 标量字段 | 用于过滤，字段清单见附录 6.4 |
| 非零项上限 | 截断至前 256 个词元 | 控制稀疏向量体积与检索开销 |

**稀疏向量的存储格式**

| 项 | 说明 |
|---|---|
| 结构 | 词元下标 → 权重的映射 |
| 下标范围 | 词元表大小以内（约 25 万） |
| 权重 | 非负有限浮点数 |
| 截断策略 | 按权重降序保留前 256 项，其余丢弃 |

**向量库与业务库的关系**

| 关系 | 说明 |
|---|---|
| **派生关系** | 向量库全部内容可从业务库重建。**业务库是唯一真相** |
| 写入方向 | 单向：业务库 → 入库任务 → 向量库。**不存在反向写入** |
| 一致性要求 | 最终一致即可。入库为异步任务，允许短暂延迟 |
| 事务要求 | **入库无需事务**——因为幂等（按条目标识更新） |
| 可恢复性 | 依赖业务库备份。业务库备份失效则知识库需从源文件重新构建 |

**HNSW 参数取值的理由**

| 参数 | 取值 | 权衡 |
|---|---|---|
| `M = 16` | 中等连接度 | M 越大召回越高但内存与建索引时间上升。16 是通用场景的平衡点，适用于本项目十万级向量的规模 |
| `efConstruction = 64` | 建索引宽度 | 越大建索引越慢但索引质量越高。64 在构建时间与召回之间取平衡 |
| 检索期 `ef` | 运行时指定，建议 2~4 倍于 `limit` | 与建索引参数分开，可在线调整而不重建索引 |

## 3. 表结构详细设计

**通用约定（适用于本章全部表）**

1. 本章所有表均为 `public` schema 下的业务表，表名以 `mg_` 开头
2. **除 `mg_tenant` 外**，全部表含审计字段 7 个（定义见 1.3 节）。`mg_tenant` 是租户本身的定义表，不含 `tenant_id`——这是唯一的例外，仓储基类需对此表单独处理
3. 主键统一为 `id varchar(32) DEFAULT replace(gen_random_uuid()::text, '-', '')`
4. 不使用物理外键，关联字段见 1.4 节
5. 字段表格中的"审计字段"一行，表示该表含 1.3 节定义的 7 个字段

| `idx_mg_audit_trace` | 复合 | `tenant_id`, `trace_id` | 按追踪标识关联链路 |

**业务说明**

**本表是审计体系的核心，具有四个强制属性**（架构文档 §8.5）：

| 属性 | 实现方式 |
|---|---|
| **只追加** | 不提供 `update_by` / `update_time` / `del_flag` / `remark` 字段——不是"靠约定不用"，而是**结构上不支持** |
| **不可修改** | 数据库层用 `BEFORE UPDATE OR DELETE` 触发器直接抛异常（见 init.sql 末尾）。**不使用 `REVOKE` 权限**，理由见下方说明 |
| **无关联** | 除 `tenant_id` 外不建任何逻辑关联字段，只存标识快照。业务数据归档后审计仍可读 |
| **保留 1 年** | 由应用层定时任务执行归档（`NFR20`），归档动作本身也写审计（`action_type='DATA_ARCHIVE'`） |

**本表刻意不含审计字段中的 4 个**：没有 `update_*` 与 `del_flag`、`remark`。理由见上表第一行——**用结构约束代替约定约束**，比"写在文档里说不要改"可靠得多。`patient_hash` 存哈希不存明文（`AC-F53-3`）。

**为什么用触发器而不是 `REVOKE` 权限**

| 手段 | 有效性 | 采用与否 |
|---|---|---|
| `REVOKE UPDATE, DELETE ON mg_audit_log FROM <角色>` | 对普通角色有效，但**对超级用户无效**。开发环境默认以 `postgres` 超级用户连接，此时约束形同虚设，反而给人虚假的安全感 | ❌ 不采用 |
| `BEFORE UPDATE OR DELETE` 触发器 `RAISE EXCEPTION` | 对**所有角色（含超级用户）**均有效，且不依赖连接身份 | ✅ 采用 |

触发器实现见 init.sql 末尾：用一个通用函数挂到本表上，任何 UPDATE 或 DELETE 直接抛出异常并提示走归档流程。

**对象键命名规则**

```
{tenant_id}/{biz_type}/{yyyyMM}/{file_id}.{ext}

示例：a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6/VOICE_INPUT/202610/9f8e7d6c5b4a39281706f5e4d3c2b1a0.wav
```

租户前缀置于最前，便于按机构统计对象存储占用与批量清理。时间目录按上传月份切分，避免单目录文件数过多。

**业务说明**

| 属性 | 说明 |
|---|---|
| **为什么必须单独建表** | 对象存储里只有二进制，没有归属与权限信息。接口 `GET /api/v1/files/{file_id}` 必须能回答"这个文件属于哪个患者或会话、当前用户是否有权访问"——这些元信息只能落在关系库 |
| **鉴权链路** | 请求携带 `file_id` → 查本表得到 `tenant_id` / `patient_id` / `session_id` → 复用与业务表完全相同的三层权限判定（角色 + 机构 + 行级），不新增一套鉴权逻辑 |
| **与业务表的关联** | `biz_type='EMR_ATTACHMENT'` 时 `biz_ref_id` 指向 `mg_emr_document.id`；`biz_type='VOICE_INPUT'` 时 `session_id` 指向 `mg_session.id`。**不建物理外键**，与全库策略一致 |
| **物理删除** | 业务层软删除（`del_flag='1'`）后，由定时任务按保留期清理 MinIO 中的对象，并写审计（`action_type='DATA_ARCHIVE'`）。**先改数据库状态再删对象**，顺序不可颠倒 |
| **不存文件内容** | 表内只存元信息与对象键。`file_hash` 存内容摘要，不存内容本身 |
| **不进入缓存** | 文件元信息**不缓存到 Redis**（与 §6.7 的缓存清单一致）。否则软删除后缓存未失效，会造成越权下载 |

## 4. 完整初始化脚本（init.sql）

**执行方式**

```bash
psql -h localhost -p 5432 -U medguide -d medguide -f deploy/postgres/init.sql
```

**脚本特征**

| 特征 | 说明 |
|---|---|
| 扩展 | **仅一行** `CREATE EXTENSION IF NOT EXISTS vector;`（主键用到 `gen_random_uuid()` 为 PG13+ 内置，无需 `pgcrypto`） |
| 触发器 | **仅 1 个**：`mg_audit_log` 的防篡改触发器（阻止 UPDATE 与 DELETE，见 3.6.2）。其余表的 `update_time` 与 `update_by` 由应用层维护 |
| 幂等性 | 全部使用 `CREATE TABLE IF NOT EXISTS` / `CREATE INDEX IF NOT EXISTS`，可重复执行 |
| 注释 | 所有表、所有字段、所有索引均带注释 |
| 外键 | **无**。逻辑关联字段另建索引 |
| 种子数据 | 使用固定 32 位标识，`ON CONFLICT DO NOTHING` 保证可重复执行 |
| 行级安全 | **不含 RLS 语句**（一期不启用）。启用脚本单独放在 `deploy/postgres/migrations/001_enable_rls.sql`，与 6.5 节的迁移步骤对应 |

**与 Alembic 的分工（重要）**

本脚本与 Alembic 的职责边界必须写死，否则首次启动就会冲突：

| 阶段 | 由谁负责 | 说明 |
|---|---|---|
| 首次建库 | **init.sql** | 由 `docker-entrypoint-initdb.d` 在容器**首次**初始化时自动执行，建出全部表、索引与种子数据 |
| 打基线 | `alembic stamp head` | 建表完成后**执行一次**，把当前结构标记为迁移基线，不重复建表 |
| 后续变更 | **Alembic** | 此后的任何结构变更一律生成 revision 脚本；禁止手工改表（`NFR33`） |

**为什么不是"全由 Alembic 建表"**：容器首次初始化若只建扩展，应用启动还需额外一步 `alembic upgrade head`，多了一个可能被遗漏的手工步骤——而这个步骤一旦遗漏，应用会因为找不到表而启动失败。以 init.sql 建表、Alembic 接管后续变更，是「首次零手工」与「后续可追溯」之间的折中。

> ⚠️ **禁止**在未执行 `alembic stamp head` 的情况下直接运行 `alembic upgrade head`——会因表已存在而报错。

## 5. 数据流转说明

### 5.1 任务创建与执行数据流

本系统中的"任务"指**知识库入库任务**——它是唯一具有"创建 → 排队 → 分阶段执行 → 完成"完整生命周期的异步任务。

```
管理后台        接口层        服务层        mg_kb_ingest_task      异步执行器
   │             │             │                   │                  │
   │ 点击入库 ──→│             │                   │                  │
   │             │ 校验权限     │                   │                  │
   │             ├────────────→│                   │                  │
   │             │             │ ① 检查是否有未完成任务                │
   │             │             ├──────────────────→│                  │
   │             │             │←─ 查询部分索引 idx_mg_kbing_         │
   │             │             │   tenant_status（只扫未完成任务）      │
   │             │             │                   │                  │
   │             │             │ ② INSERT 任务记录                    │
   │             │             │   status='PENDING'                    │
   │             │             ├──────────────────→│                  │
   │             │             │                   │                  │
   │             │             │ ③ 写审计日志（同事务）                 │

   │             │             │                   │                  │
   │←─ 任务编号 ─┤             │                   │                  │
   │             │             │ ④ 投递任务 ───────┼─────────────────→│
   │             │             │                   │                  │
   │             │             │                   │←─ ⑤ 更新         │
   │             │             │                   │   status=        │
   │             │             │                   │   'RUNNING'      │
   │             │             │                   │   stage='VALIDATE'│
   │             │             │                   │                  │
   │             │             │                   │←─ ⑥ 读 mg_kb_entry│
   │             │             │                   │   执行完整性校验  │
   │             │             │                   │                  │
   │             │             │      ┌─── 校验失败 ───┐              │
   │             │             │      │  写入 error_json│              │
   │             │             │      │  status='FAILED'│              │
   │             │             │      │  ★ 整批不写入   │              │

   │             │             │                   │                  │
   │             │             │                   │←─ ⑦ 差异比对     │

   │             │             │                   │   统计增/改/停用  │
   │             │             │                   │                  │
   │             │             │                   │←─ ⑧ 向量化       │
   │             │             │                   │   stage='EMBED'  │
   │             │             │                   │   逐批更新 progress│
   │             │←─ 轮询进度 ─┤                   │                  │
   │             │             │                   │                  │
   │             │             │                   │←─ ⑨ 写入向量库   │
   │             │             │                   │   stage='WRITE'  │
   │             │             │                   │   按 entry_code  │
   │             │             │                   │   upsert（幂等）  │

   │             │             │      │ INSERT mg_golden_query_run │  │
   │             │             │      │  记录 pass_rate 与         │  │
```

**数据流中的三个关键设计点**

| 设计点 | 对应的表与索引 | 作用 |
|---|---|---|
| **防重复触发** | 查询 `mg_kb_ingest_task` 的部分索引 `idx_mg_kbing_tenant_status` | 该索引只索引 `PENDING` / `RUNNING` 状态的行，通常只有个位数，查询极快 |
| **校验失败即中止** | `mg_kb_ingest_task.error_json` + `failed_count` | `AC-F29-2` 要求任一条目校验失败则整批不写入；失败明细必须可展示 |
| **验证作为终点** | `mg_golden_query_run` | 入库不是"写完就完"，必须跑回归验证。通过率低于基线时 `is_regression='1'` 触发告警 |

**任务与知识库版本的关系**

```
mg_kb_ingest_task  ──执行──→  向量库（外部）
        │
        └──触发──→  mg_golden_query_run
                          │
                          └──记录 kb_version ──→ mg_kb_publish（发布时才写）
```

**注意**：入库任务运行时**不写 `mg_kb_publish`**——发布是独立动作。入库只让数据"可检索"，发布才产生版本快照。

```
编排层        检索组件        向量化        向量库          mg_kb_entry
   │             │              │             │                 │
   │ 查询（症状实体 + 主诉）     │             │                 │
   ├────────────→│              │             │                 │
   │             │ ① 构造查询    │             │                 │
   │             │              │             │                 │
   │             │ ② 向量化 ───→│             │                 │
   │             │              │ 一次推理     │                 │
   │             │              │ 产出两路向量 │                 │
   │             │←─ 稠密+稀疏 ─┤             │                 │
   │             │              │             │                 │
   │             │ ③ 双路并行检索              │                 │
   │             ├─────────────────────────→  │                 │
   │             │   带 tenant_id 强制过滤      │                 │
   │             │   带 dept_code / 人群过滤    │                 │
   │             │←─ 两路结果 ──────────────────┤                 │
   │             │              │             │                 │
   │             │ ④ 融合排序（可配置模式）      │                 │
   │             │   仅语义 / 仅词元 / RRF 融合  │                 │
   │             │              │             │                 │
   │             │ ⑤ 精排（可跳过）             │                 │
   │             ├─────────────────────────→  │ 外部精排服务     │
   │             │←─ 重排结果 ──────────────────┤                 │
   │             │              │             │                 │
   │             │ ⑥ 按科室聚合出候选与置信度    │                 │
   │             │ ⑦ 附加指南片段 ─────────────┼────────────────→│
   │             │              │             │  ← 读 mg_kb_entry│
   │←─ 候选科室 ─┤              │             │    补充来源与正文 │
   │             │              │             │                 │
   │ ⑧ 写 mg_triage_result      │             │                 │
   │   candidates_json（JSONB）  │             │                 │
   │   evidence_json             │             │                 │
   │   retrieval_mode            │             │                 │
   │   kb_version                │             │                 │
```

**检索过程涉及的字段与它们的用途**

| 写入字段 | 位置 | 用途 |
|---|---|---|
| `candidates_json` | `mg_triage_result` | 候选科室与置信度，供医生端展示鉴别诊断候选（`R02`） |
| `evidence_json` | `mg_triage_result` | 命中的症状与引用的指南条目标识，供医生查看判断依据（`F17`） |
| `retrieval_mode` | `mg_triage_result` | 本次用了哪种检索模式，**这是判断混合检索增益的原始数据** |
| `kb_version` | `mg_triage_result` | 决策依据的知识库版本，用于事后复盘 |

**检索的三层过滤（缺一不可）**

```
第一层  向量库分区     tenant_id 分区键      → 机构级物理隔离
第二层  向量库标量过滤  tenant_id + dept_code → 精确过滤（NFR15）
第三层  应用层校验     结果归属校验           → 兜底（防止过滤被误改）
```

```
    │ ③ 敏感操作发生   │              │                 │                 │
    │  （读病历/挂号/  │              │                 │                 │
    │    分诊确认）    │              │                 │                 │
    ├───────────────┼──────────────┼────────────────→│                 │
    │                │              │  同事务写入审计  │                 │
    │                │              │  ★ 写入失败则    │                 │
    │                │              │    业务失败      │                 │
    │                │              │                 │                 │
    │ ④ 出域守卫拦截   │              │                 │                 │
    ├───────────────┼──────────────┼────────────────→│                 │
    │                │              │  action_type=   │                 │
    │                │              │  'EGRESS_BLOCK' │                 │
    │                │              │                 ├────────────────→│
    │                │              │                 │  拦截次数 > 0   │
    │                │              │                 │  立即告警        │
    │                │              │                 │                 │
    │ ⑤ 请求结束       │              │                 │                 │
    ├───────────────→│ 访问日志      │                 │                 │
    │                │ ★ 不记请求体  │                 │                 │
```

**四类可观测数据的落点对照**

| 数据类别 | 落点 | 保留期 | 关键约束 |
|---|---|---|---|
| 访问日志 | 标准输出 → 集中采集 | 30 天 | 不记请求体与响应体 |
| 应用日志 | 标准输出 → 集中采集 | 30 天 | 患者标识用哈希；不记提示词全文 |
| **审计记录** | `mg_audit_log`（专用表） | **不少于 1 年** | **只追加、不可修改、与业务同事务** |
| 追踪数据 | 追踪系统（不落业务库） | 按追踪系统策略 | 只记标识与统计量，不记原文 |

**为何追踪数据不落业务库**：追踪数据量远大于业务数据（每个节点一条跨度），写入频率高且无强一致性要求。放进业务库会挤占连接池并影响主库性能。**但追踪标识 `trace_id` 会写入 `mg_audit_log`**，这样审计记录可以关联到完整链路。

### 5.4 数据清理与归档数据流

```
定时任务            各业务表                       mg_audit_log
   │                    │                              │
   │ ① 按保留期扫描      │                              │
   ├───────────────────→│                              │
   │  会话保留期 90 天    │  查询 mg_session             │
   │  （系统配置可调）    │  WHERE started_time < 阈值    │
   │                    │                              │
   │ ② 归档或清理        │                              │
   ├───────────────────→│                              │
   │  会话及其关联数据    │  mg_session                  │
   │  （消息/结论/病历）  │  mg_session_message          │
   │                    │  mg_triage_result            │
   │                    │  mg_emr_record               │
   │                    │                              │
   │ ③ 记录归档动作      │                              │
   ├───────────────────┼─────────────────────────────→│
   │                    │                              │  action_type=
   │                    │                              │  'DATA_ARCHIVE'
   │                    │                              │
   │ ④ 审计记录清理      │                              │
   │  （保留期 ≥ 1 年）  │                              │
   ├────────────────────┼─────────────────────────────→│
   │                    │                              │  清理动作
   │                    │                              │  同样写审计
```

**清理策略的边界**

| 数据 | 是否清理 | 说明 |
|---|---|---|
| 预问诊会话及其关联数据 | ✅ 按保留期（默认 90 天） | 保留期可由租户配置 |
| 审计记录 | ✅ 按保留期（不少于 1 年） | **清理动作本身也要写审计** |
| 知识库条目（含停用） | ❌ **永不物理删除** | `R09` 要求不提供物理删除。停用条目的数据与变更记录长期保留 |
| 知识库变更记录 | ❌ 不清理 | 只追加表，是条目历史的唯一来源 |
| 病历类数据 | ❌ 不自动清理 | 医疗数据特性，按机构策略处理 |
| 黄金查询集与回归记录 | ❌ 不清理 | 是检索质量的历史基线 |

**禁止事项**

| 禁止 | 理由 |
|---|---|
| 使用数据库事件调度或触发器执行清理 | 与"不使用触发器"的设计约定冲突；清理是有副作用的操作，应在应用层可见可控 |
| 清理时不写审计 | `NFR48` 要求归档动作留痕 |
| 对知识库条目执行物理删除 | 违反 `R09`，且会破坏变更历史的完整性 |

```python
"""Milvus 集合初始化。开发形态与交付形态仅连接地址不同，代码不变。"""

from pymilvus import DataType, Function, FunctionType, MilvusClient

DIM = 1024
HNSW_PARAMS = {"M": 16, "efConstruction": 64}
SPARSE_INDEX = {"index_type": "SPARSE_INVERTED_INDEX", "metric_type": "IP", "params": {}}


def create_collection(client, name: str, *, with_sparse: bool, partition_key: bool,
                      scalar_fields: list[tuple[str, DataType]], enable_partition: bool = True):
    if client.has_collection(name):
        client.drop_collection(name)

    schema = client.create_schema(auto_id=False, enable_dynamic_field=True)
    schema.add_field("id", DataType.VARCHAR, is_primary=True, max_length=32)
    schema.add_field("text", DataType.VARCHAR, max_length=4096, enable_analyzer=True)
    schema.add_field("dense_vec", DataType.FLOAT_VECTOR, dim=DIM)

    if with_sparse:
        schema.add_field("sparse_vec", DataType.SPARSE_FLOAT_VECTOR)

    if partition_key and enable_partition:
        schema.add_field("tenant_id", DataType.VARCHAR, max_length=32, is_partition_key=True)
    elif partition_key:
        schema.add_field("tenant_id", DataType.VARCHAR, max_length=32)

    for field_name, dtype in scalar_fields:
        schema.add_field(field_name, dtype)

    index_params = client.prepare_index_params()
    index_params.add_index("dense_vec", index_type="HNSW", metric_type="COSINE", params=HNSW_PARAMS)
    if with_sparse:
        index_params.add_index("sparse_vec", **SPARSE_INDEX)

    client.create_collection(name, schema=schema, index_params=index_params)
    client.load_collection(name)
    print(f"  已创建：{name}")


def main(uri: str = "./data/milvus/dev.db"):
    client = MilvusClient(uri)
    print(f"连接 Milvus：{uri}")
    print("创建集合：")

    create_collection(
        client, "kb_dept_expertise", with_sparse=True, partition_key=True,
        scalar_fields=[("dept_code", DataType.VARCHAR), ("sub_specialty", DataType.VARCHAR)],
    )
    create_collection(
        client, "kb_symptom_disease", with_sparse=True, partition_key=True,
        scalar_fields=[
            ("icd10_code", DataType.VARCHAR), ("dept_code", DataType.VARCHAR),
            ("age_group", DataType.VARCHAR), ("gender", DataType.VARCHAR),
        ],
    )
    create_collection(
        client, "kb_guideline", with_sparse=True, partition_key=True,
        scalar_fields=[
            ("disease", DataType.VARCHAR), ("evidence_level", DataType.VARCHAR),
            ("publish_year", DataType.INT64),
        ],
    )
    # 编码对照为全局共享，不分区、不带稀疏向量
    create_collection(
        client, "kb_icd10", with_sparse=False, partition_key=False,
        scalar_fields=[("code", DataType.VARCHAR), ("chapter", DataType.VARCHAR)],
    )
    create_collection(
        client, "kb_drug_safety", with_sparse=False, partition_key=True,
        scalar_fields=[
            ("drug_id", DataType.VARCHAR), ("contraindication_type", DataType.VARCHAR),
            ("population", DataType.VARCHAR),
        ],
    )
    create_collection(
        client, "kb_case", with_sparse=False, partition_key=True,
        scalar_fields=[("dept_code", DataType.VARCHAR), ("diagnosis", DataType.VARCHAR)],
    )
    # 病历文书：除租户外还需按患者过滤
    create_collection(
        client, "kb_emr_document", with_sparse=True, partition_key=True,
        scalar_fields=[
            ("patient_hash", DataType.VARCHAR), ("doc_type", DataType.VARCHAR),
            ("section", DataType.VARCHAR), ("record_time", DataType.INT64),
        ],
    )

    print(f"\n完成，共 {len(client.list_collections())} 个集合")


if __name__ == "__main__":
    main()
```

**稀疏向量的写入格式**（由向量化模型产出，非向量库生成）

```python
def to_milvus_sparse(lexical_weights: dict, top_k: int = 256) -> dict[int, float]:
    """{token_id: weight} → {index: value}，按权重降序截断至 top_k。"""
    pairs = []
    for key, value in lexical_weights.items():
        try:
            index, weight = int(key), float(value)
        except (TypeError, ValueError):
            continue
        if weight > 0:
            pairs.append((index, weight))
    pairs.sort(key=lambda kv: kv[1], reverse=True)
    return dict(pairs[:top_k])
```

**HNSW 参数的调整时机**

| 数据规模 | `M` | `efConstruction` | 说明 |
|---|---|---|---|
| < 10 万 | 16 | 64 | **当前取值**，构建快、召回足够 |
| 10 万 ~ 100 万 | 24 | 128 | 提升召回，构建时间上升 |
| > 100 万 | 32 | 200 | 内存与构建时间显著上升，需评估 |

调整 `efConstruction` **需要重建索引**；检索期的 `ef` 参数可在线调整，无需重建。

### 6.5 RLS 启用迁移路径

当前**不启用**数据库级行级安全策略（理由见 1.6 节），但表结构已完整预留。将来需要时按以下步骤启用，**不需要修改表结构**。

> ⚠️ **init.sql 中不含任何 RLS 语句**。启用 RLS 是一次真实的 DDL 操作，一旦执行立即生效——若此时应用层尚未实现会话变量注入，**所有查询会返回空结果**。注意这里不是抛异常，而是**静默地查不到数据**，排查成本很高。因此启用顺序必须是：先实现应用层注入 → 灰度验证 → 再启用 RLS。完整启用脚本见 `deploy/postgres/migrations/001_enable_rls.sql`。

**前置条件（已满足）**

| 条件 | 状态 |
|---|---|
| 所有业务表带 `tenant_id` | ✅ 已满足（22/23，例外为 `mg_tenant`） |
| 复合索引以 `tenant_id` 为首列 | ✅ 已满足 |
| 应用层以统一方式获取当前租户 | ✅ 已满足（请求上下文） |

**迁移步骤**

| 步骤 | 操作 | 说明 |
|---|---|---|
| 1 | 为每张业务表启用 RLS | `ALTER TABLE <表名> ENABLE ROW LEVEL SECURITY;` |
| 2 | 为每张表创建隔离策略 | 见下方策略模板 |
| 3 | 应用层在每个事务开始时设置会话变量 | `SELECT set_config('app.current_tenant', :tenant_id, true);` |
| 4 | 连接池配置 | **必须在事务内设置**（`set_config` 第三参数为 `true` 表示事务级）；使用会话级设置会因连接复用导致租户串号 |
| 5 | 业务角色不得具备 `BYPASSRLS` | 否则策略失效 |
| 6 | 灰度验证 | 先对只读表启用，验证后再覆盖写表 |

**策略模板**

```sql
-- 对每张业务表执行（示例：mg_session）
ALTER TABLE mg_session ENABLE ROW LEVEL SECURITY;

-- 隔离策略：只允许访问当前租户的数据
CREATE POLICY p_mg_session_tenant ON mg_session
    FOR ALL
    TO medguide_app
    USING (tenant_id = current_setting('app.current_tenant', true))
    WITH CHECK (tenant_id = current_setting('app.current_tenant', true));

-- 说明：
--   USING       控制"能看到哪些行"
--   WITH CHECK  控制"能写入哪些行"，防止插入其他租户的数据
--   current_setting 第二参数 true 表示缺失时不报错（返回 NULL），
--   此时策略不匹配任何行 —— 即"未设置租户则查不到任何数据"，这是安全的默认行为
```

**三个必须注意的实现细节**

| 细节 | 说明 |
|---|---|
| **会话变量必须事务级** | 用 `set_config(..., true)` 而非 `SET`。连接池复用连接时，会话级设置会残留，导致下一个请求读到上一个租户的数据 |
| **未设置变量时查不到数据** | 这是刻意的安全默认——宁可查不到，也不能查到别人的。开发环境要特别注意：忘记设置会表现为"表里明明有数据却查不出来" |
| **不适用于 `mg_tenant` 表** | 该表无 `tenant_id`，且是租户自身的管理表，需要单独设计访问策略（通常只允许机构管理角色访问） |

**启用后的收益与代价**

| 项 | 说明 |
|---|---|
| 收益 | 应用层即使漏写租户过滤，数据库层仍会拒绝跨租户访问（纵深防御） |
| 代价 | 每张表多一次策略判定（性能影响通常在 1% 以内）；开发调试复杂度上升；连接池配置需要谨慎处理 |

### 6.7 Redis 键设计与缓存契约

Redis 在本系统承担四类职责：**缓存、接口限流、WebSocket 消息广播、一次性票据**。本节给出键命名契约——键名是跨模块协作的接口，必须唯一确定，否则不同模块写出的键会互相覆盖，或写了却命中不到。

**键命名规范**

```
mg:{域}:{租户标识}:{业务标识}[:{子标识}]
```

| 规则 | 说明 |
|---|---|
| 统一前缀 `mg:` | 便于在共享实例上区分应用，也便于用 `SCAN mg:*` 排查 |
| 域名为固定枚举 | 见下方键清单；新增域必须在本节登记 |
| 租户标识必填 | 除全局键（如 WebSocket 票据）外，`tenant_id` 必须出现在键中 |
| 禁止个人标识明文 | 手机号、身份证号、姓名一律先用哈希（与 `patient_hash` 同一算法）后再入键 |
| 禁止使用 `KEYS` | 生产环境一律用 `SCAN`；批量失效优先用「键前缀 + 版本号」方案 |

**键清单**

| 用途 | 键模式 | 数据结构 | TTL | 失效方式 | 责任模块 |
|---|---|---|---|---|---|
| 会话热数据 | `mg:sess:{tenant_id}:{session_id}` | Hash | 滑动过期，上限 2h | 会话结束时 DEL | 会话服务 |
| 会话消息序号 | `mg:sess:seq:{tenant_id}:{session_id}` | String（自增） | 同会话热数据 | 会话结束时 DEL | 会话服务 |
| 知识库检索缓存 | `mg:kbc:{tenant_id}:{query_hash}:{mode}` | String(JSON) | 10 min | 知识库入库完成后按前缀批量 DEL | 检索组件 |
| 机构配置 | `mg:cfg:{tenant_id}` | Hash | 30 min | 配置变更时 DEL | 配置服务 |
| 号源快照 | `mg:slot:{tenant_id}:{dept_code}:{date}` | String(JSON) | 5 min | 自然过期 | 挂号能力 |
| 限流计数 | `mg:rl:{dimension}:{tenant_id}:{key}:{window}` | String（计数） | 与窗口一致 | 窗口滚动 | 中间件 |
| WebSocket 票据 | `mg:ws:ticket:{ticket_id}` | Hash | 60 s | **用后即删**（`GETDEL`） | 接口层 |
| WebSocket 广播频道 | `mg:ws:chan:{session_id}` | Pub/Sub | — | 连接断开即退订 | 接口层 |
| 幂等键 | `mg:idem:{tenant_id}:{idempotency_key}` | String（响应摘要） | 24 h | 自然过期 | 中间件 |

`mode` 取值与检索三模式一致：`DENSE` / `SPARSE` / `HYBRID`（对应 `F30` 的验证台）。
`dimension` 取值与 04 文档 §9 的限流维度一一对应：`ip` / `user` / `device` / `session` / `interface`。

**数据库编号划分（重要）**

| db | 用途 | 说明 |
|---|---|---|
| 0 | 业务缓存（上表所有 `mg:` 键） | — |
| 1 | Celery broker | 与业务缓存分离。否则运维误执行 `FLUSHDB` 时，会把消息队列一起清空 |
| 2 | Celery result backend | 同上 |

**明确不缓存的内容**

| 不缓存 | 理由 |
|---|---|
| 患者病历与既往史（`mg_emr_record` / `mg_emr_document`） | 敏感数据，且必须读到最新记录 |
| 审计记录（`mg_audit_log`） | 只追加、强一致，缓存无收益且有风险 |
| 权限判定结果 | 权限变更必须立即生效 |
| 文件元信息（`mg_file`） | 软删除后若缓存未失效，会导致越权下载 |
| 分诊结论（`mg_triage_result`） | 会被医生修正，一致性优先 |

**与架构文档的对应**：本节是 02 文档 §7.5「缓存策略」的执行级细化——策略层只回答「缓存什么、什么时候失效」，本节补充「键叫什么、用什么结构、TTL 具体多少、放在哪个 db」。

**多实例场景**：键清单中的 `mg:ws:chan:{session_id}` 承担 WebSocket 消息广播——同一会话的消息需路由到持有该连接的实例。这是 02 文档 §9.5 可扩展性的实现基础。
